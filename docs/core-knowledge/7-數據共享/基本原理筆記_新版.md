# Delta Sharing 完整筆記彙整

## 📌 什麼是 Delta Sharing？

Delta Sharing 是 Databricks 開發的開源協議（open-source protocol），讓組織能夠安全、即時地跨組織分享資料，且**無需進行資料複製或移動**。

> "Delta Sharing 是 Databricks 的創新技術，它革新了組織分享與交換資料的方式。它提供一種簡單、安全且開放的方法，讓資料提供者和消費者能夠跨組織即時分享資料，不論他們使用哪種計算平台。" — Ron L'Esteve

---

## 🎯 核心目的：告別資料複製／匯出

### 傳統做法的問題
- 定期將 Delta table 匯出成另一份資料（JSON/Parquet/SFTP/email…）
- 產生多份「truth」版本，同步脆弱且容易出錯
- 成本高昂（ingress/egress 費用 + 重複執行）

### Delta Sharing 的解決方案
讓接收者**直接讀取來源的 live data 或 snapshot**，避免管理大量 export job 與狀態同步問題。

---

## 🔧 Delta Sharing 如何運作？

Delta Sharing 透過簡化的 REST 協議（REST protocol），授予對雲端資料集特定部分的存取權限：

1. **資料提供者**建立「Shares」（唯讀的資料物件集合）和「Recipients」（取得存取權的個人或組織）
2. 授予存取權後，接收者會收到**短效的預簽名 URLs**（presigned URLs），可直接存取資料所在的雲端儲存空間
3. 協議建構在 **Delta Lake** 之上，提供 ACID 交易與可擴展的 metadata 處理，確保資料完整性

---

## 👥 三個核心角色

### 1. Provider（資料提供方）
- 擁有資料資產（schemas/tables/views…）
- 負責建立分享與權限邊界

### 2. Share（分享單位）
- **邏輯發布單位**：將可共享的資料資產組成一組
- 結構：Share → Schemas → Tables/Views（樹狀結構）
- **關鍵概念**：Share **不是把資料送出去**，而是定義「哪些資產可被讀取」

### 3. Recipient（接收者）
- 是一個 principal（可代表 user / team / business unit / system）
- 使用 **Recipient Profile File（JSON）** 取得存取資訊：
  - `endpoint`：Delta Sharing server URL
  - `bearerToken`：存取 token
  - `expirationTime`（可選）：token 到期時間
- **限制**：不支援群組內個別使用者的細粒度權限差異；需要差異化就必須發放不同的 recipient profile

## 🌐 四種分享模式（Four Modes）

Delta Sharing 支援四種不同的分享模式，以滿足不同組織需求：

### 1. Databricks to Databricks (D2D)
- 提供者與接收者都使用 Databricks 平台
- **功能最完整**：支援 notebook 分享、AI 模型分享、完整的治理功能

### 2. Databricks to Open (D2O)
- Databricks 使用者分享資料給非 Databricks 接收者
- 使用基於 token 的憑證和啟動連結

### 3. Open to Databricks (O2D)
- 非 Databricks 提供者分享資料給 Databricks 接收者

### 4. Open to Open (O2O)
- 任何開源平台之間的資料分享，無需使用 Databricks

---

## 🔄 Delta Sharing Server（Sharing Service）

### 服務定位
實作 Delta Sharing Protocol 的服務（可為 Databricks 託管或 OSS 參考實作）

### 主要責任
1. **Authenticate / Authorize**：使用 bearer token 進行驗證與授權
2. **Metadata Broker**：回傳 schema/table/view 的 metadata（包含 properties、schema）
3. **Snapshot File Access**：提供讀取特定 table snapshot/version 所需的 **presigned file access**

---

## 🌟 核心優勢與特性

### 1. 即時存取，無需複製（Real-Time Access Without Replication）
- 提供即時資料存取，無需建立副本
- 接收者始終使用最新資訊
- 降低儲存成本與安全風險

### 2. 跨平台相容性（Cross-Platform Compatibility）
- 開源特性允許整合各種工具：
  - **資料科學工具**：Pandas, Spark, Jupyter Notebooks
  - **商業智慧工具**：Power BI, Tableau, Excel
- 不論接收者是否使用 Databricks 都能使用

### 3. 細粒度存取控制（Fine-Grained Access Control）
- 資料擁有者可指定詳細權限
- 可控制誰能存取特定的 datasets、tables 或個別 columns
- 確保敏感資訊受到保護

### 4. 內建安全與治理（Built-in Security and Governance）
- 與 Unity Catalog 整合時提供：
  - 集中式治理
  - 稽核功能
  - 所有資料存取請求的完整記錄

## 🔐 REST API：底層協議操作

### API 特性
- REST 是 protocol 層的操作接口（多數情境使用 client，不會直接呼叫 API）
- 所有 API 都需要 Header：`Authorization: Bearer {token}`
- 支援 Pagination：`maxResults` + `pageToken/nextPageToken`

### 常見 Introspection API
```
GET {prefix}/shares                                      # 列出所有 shares
GET {prefix}/shares/{share}                              # 取得特定 share
GET {prefix}/shares/{share}/schemas                      # 列出 schemas
GET {prefix}/shares/{share}/schemas/{schema}/tables      # 列出 tables
GET {prefix}/shares/{share}/all-tables                   # 列出所有 tables
```

## 💻 Client 使用方式

### Spark / PySpark
```python
# 安裝 delta-sharing client（Python 套件 + Spark JAR）
# 使用 profile file + table path
spark.read.format("deltaSharing") \
  .load("<profile>#<share>.<schema>.<table>")
```

### Spark SQL Extension
```sql
-- 建立指向 remote share table 的表
CREATE TABLE my_shared_table 
USING deltaSharing 
LOCATION '<profile>#share.schema.table';

-- 後續像查詢一般表
SELECT * FROM my_shared_table;
```

### Streaming
```python
# 讀取 shared table 的增量版本
spark.readStream \
  .format("deltaSharing") \
  .option("startingVersion", "0") \
  .load("<profile>#<share>.<schema>.<table>")
```

## 🔗 與 Unity Catalog 整合

Delta Sharing 完全整合在 Databricks Unity Catalog 中，Unity Catalog 作為 metastore 服務：

> "Unity Catalog 透過 Delta Sharing 實現安全的資料分享。Delta Sharing 協議是組織內不同實體可以採用並利用的共同語言，用於資料分享與協作。"

### 整合優勢
- 即時分享儲存在 Unity Catalog 中的資料資產集合，無需複製
- 在提供者端維持治理優勢
- 集中式的存取控制與稽核

## ⚠️ 限制與注意事項

### 主要限制
1. **僅支援 Delta 格式的表**（只能分享 Delta tables）
2. **唯讀分享**（read-only shares）
3. **無法處理 views**
4. 存在平台特定的資源限制與配額

### 安全最佳實踐
- **Bearer token 應該設定到期時間並定期輪替**（長效 token 是安全反模式）
- 建議提供 re-authentication API/流程，讓外部 recipient 可重新取得 profile/token
- 妥善管理 presigned URLs 的有效期限

---

## 📝 一句話總結

Delta Sharing 透過「**Share（發佈清單）+ Recipient（token/profile）+ Sharing Server（REST + metadata + presigned snapshot access）**」架構，讓外部或跨雲端的計算平台能直接讀取來源 Delta table，避免資料複製造成的同步問題、成本增加與多版本 truth 的困擾。
