優化機制速覽（考前快速對照）
	•	Predictive Optimization（PO）：自動判斷哪些 UC Managed tables 需要維護，並用 serverless jobs 排程執行 ANALYZE / OPTIMIZE / VACUUM；費用走 serverless jobs SKU，可用 system tables 追蹤。 ￼
	•	Liquid Clustering（CLUSTER BY … / AUTO）：用「clustering keys」改善 data skipping 與查詢效能；CLUSTER BY AUTO 會讓系統自動選/調整 keys（需 DBR 15.4+）。 ￼
	•	Optimized Writes（delta.autoOptimize.optimizeWrite）：寫入時優化檔案布局；table property 預設值不是固定 true（default: none），通常以 table-scoped 設定管理較清楚。 ￼
	•	Auto Compaction（delta.autoOptimize.autoCompact）：自動把小檔案合併；可用 table property 或 session 設定啟用（default: none）。 ￼
	•	Deletion Vectors（DV）（delta.enableDeletionVectors）：UPDATE/DELETE/MERGE 以「軟刪/軟改」加速；新表是否預設啟用由 workspace admin 設定控制；DBR 14.2+ 搭配 DV 支援 row-level concurrency。 ￼
	•	Tune file size for rewrites（delta.tuneFileSizesForRewrites=true）：官方建議 MERGE/DML 很多的表打開，會把目標檔案尺寸調低以加速重寫型操作。 ￼
	•	OPTIMIZE / VACUUM / ANALYZE：
	•	OPTIMIZE：合併檔案、套用 clustering 的物理重排；
	•	VACUUM：清舊版本檔案（影響 time travel 保留）；
	•	ANALYZE：收集統計供最佳化器使用；PO 會對 UC managed tables 自動跑 ANALYZE。 ￼
	•	Data Skipping / Indexed Cols：Delta 會依統計做檔案略讀；可調 delta.dataSkippingNumIndexedCols 擴大索引欄位數（考題常出「是表屬性、不是語法魔法」）。 ￼

Databricks 效能優化決策手冊（2026）考前快速瀏覽版

（同樣架構：場景 → 手段 → 驗證）

0) 決策順序（背這個）
	1.	先判斷表型：UC Managed vs External
	2.	再判斷工作負載：append-only / merge-heavy / streaming-heavy / BI-heavy
	3.	再判斷查詢型：點查 / 範圍掃描 / 多維篩選 / 大聚合
	4.	最後看維護方式：PO 自動維護 vs 你要手動排程

⸻

1) 表型決策樹（考點最高）

A. Unity Catalog Managed Tables（首選）

關鍵結論（考試用句）
	•	若啟用 PO：會用 serverless jobs 自動排 ANALYZE / OPTIMIZE / VACUUM，你主要工作變成「選對表型、選對 clustering」。 ￼
	•	CLUSTER BY AUTO：DBR 15.4+ 可用，會自動決定/調整 clustering keys。 ￼
	•	DV：是否新表預設啟用取決於 workspace admin 設定；DBR 14.2+ + DV 支援 row-level concurrency（遇到併發寫入題目會用到）。 ￼

你要記的不是「預設都開」，而是：
	•	autoOptimize 類（optimizeWrite/autoCompact）default: none，要用時用 table properties 管。 ￼

B. External Tables（你要自己扛維護）

關鍵結論
	•	沒 PO 幫你自動維護 → 你需要自行規劃 OPTIMIZE / VACUUM / ANALYZE（或遷移成 UC managed）。 ￼
	•	Auto compaction / optimized writes：可用 table/session 設定啟用，但 default 不是必然開。 ￼

⸻

2) 工作負載型：該用哪些手段（考試常給情境）

A. Append-only（事件流 / IoT / 日誌）

優先順序
	•	先用 Liquid Clustering（表大、查詢多變就更重要），Managed 可用 CLUSTER BY AUTO。 ￼
	•	外部表：你自己排 OPTIMIZE（重點是合併小檔，必要時再考慮其他布局策略）

陷阱句
	•	「append-only 就一定 partition by date」：不一定；只有當你查詢幾乎都靠時間切且下游依賴 hive partition 才是合理理由（否則容易帶來小檔與 metadata 負擔）。

B. MERGE-heavy（CDC / SCD / upserts）

優先順序
	•	DV（加速 DML；並與 Photon predictive I/O updates/row-level concurrency 常一起出題）。 ￼
	•	delta.tuneFileSizesForRewrites=true：官方建議「MERGE 或 DML 很多的表」啟用。 ￼
	•	Clustering keys：通常對準 merge key（或最常 join/filter 的 key）

陷阱句
	•	「DV 讓資料永久不需要 OPTIMIZE」：錯；DV 最終仍可能需要透過 OPTIMIZE 等事件把變更物理化。 ￼

C. Streaming-heavy（Structured Streaming）

優先順序
	•	小檔是主敵人：策略重點是 (1) 寫入端控檔案產生、(2) 需要時用 compaction/OPTIMIZE
	•	Clustering：CLUSTER BY AUTO 是 DDL 層；streaming 的 clustering 支援/寫法依版本與 API（不要在筆記寫死特定 .option("clusterBy",...)，以免版本差踩雷）。

陷阱句
	•	「trigger 越小越好」：常見反例；太小更容易爆小檔、拖累下游查詢與維護。

D. BI-heavy（Dashboard / 多人並發查詢）

優先順序
	•	Photon（BI 大聚合/Join 常受益）
	•	Liquid clustering（Managed + AUTO 很常是最佳路徑） ￼
	•	統計：PO 會自動 ANALYZE；外部表要手動 ANALYZE。 ￼

⸻

3) 查詢型：用什麼優化對應（考題對照）

A. 點查（高選擇性）
	•	Clustering key 對準查詢 key（或 AUTO）→ 提升 data skipping。 ￼

B. 範圍掃描（時間/日期）
	•	Clustering keys 讓時間欄位可跳檔（比盲目 partition 更彈性） ￼

C. 多維篩選（典型 BI）
	•	CLUSTER BY AUTO 讓系統依查詢模式調 keys（DBR 15.4+） ￼

D. 大聚合 / 大 Join
	•	Photon + 正確統計（CBO）是常見答案組合；PO 會自動跑 ANALYZE（UC managed）。 ￼

⸻

4) 優化套件速查（考前背誦版）
	•	PO：只要是 UC managed 且啟用 → 自動排 ANALYZE/OPTIMIZE/VACUUM，用 serverless jobs 執行與計費。 ￼
	•	CLUSTER BY AUTO：DBR 15.4+；自動決定/調整 clustering keys。 ￼
	•	DV：delta.enableDeletionVectors；新表是否預設由 admin 設定控制；DBR 14.2+ 支援 row-level concurrency。 ￼
	•	Optimized writes / Auto compaction：table properties delta.autoOptimize.optimizeWrite / delta.autoOptimize.autoCompact（default: none；建議 table-scoped 管理）。 ￼
	•	MERGE-heavy 必背：delta.tuneFileSizesForRewrites=true（官方建議）。 ￼

⸻

5) 常見反模式（考題陷阱句）
	•	把 autoOptimize.* 當成「Managed 一定預設開」→ 錯（default: none）。 ￼
	•	看到 DV 就說「不需要再做任何維護」→ 錯（仍可能需 OPTIMIZE 等觸發物理化）。 ￼
	•	把 CLUSTER BY AUTO 寫在不支援的 runtime 上 → 錯（DBR 15.4+）。 ￼
	•	把 PO 說成「省錢必勝」→ 不嚴謹（它會用 serverless jobs 跑維護，要用 system tables 監控成本）。 ￼

⸻

6) 落地檢查清單（考前 1 分鐘掃過）

新表（推薦路徑）
	•	先選 UC Managed（若可）
	•	需要自動維護 → 啟用/確認 PO（自動 ANALYZE/OPTIMIZE/VACUUM） ￼
	•	查詢多變/大表 → CLUSTER BY AUTO（DBR 15.4+） ￼
	•	MERGE-heavy → DV + tuneFileSizesForRewrites=true ￼

舊表 / External（你要自己維護）
	•	評估能否遷移 UC managed（減少維護負擔）
	•	需要寫入優化 → 用 table properties 開 optimizeWrite/autoCompact（不是幻想預設已開） ￼
	•	規劃手動維護：OPTIMIZE / VACUUM / ANALYZE（頻率依表成長與 SLA）
