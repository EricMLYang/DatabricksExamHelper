## 題目內容
### 題幹
<!-- ⚠️ 保持英文原文，不要翻譯 -->
A data engineer has a Job with multiple tasks that takes more than 2 hours to complete. In the last run, the final task unexpectedly failed.

Which of the following actions can the data engineer perform to complete this run while minimizing the execution time?

### 選項
<!-- ⚠️ 保持英文原文，不要翻譯 -->
- **A.** They need to delete the failed Run, and start a new Run for the Job.
- **B.** They can keep the failed Run, and simply start a new Run for the Job.
- **C.** They can rerun this Job Run to execute all the tasks.
- **D.** They can repair this Job Run so only the failed tasks will be re-executed.

## ✅ 正解說明
### 為什麼 D 是正確答案？

**Repair Run 只重新執行失敗的任務**：
- 成功的任務不會重跑
- 大幅減少恢復時間
- 保留原本 Run 的 context

#### Repair Run 流程
```
原始 Run（失敗）：
Task 1: ✅ 成功 (30分鐘)
Task 2: ✅ 成功 (45分鐘)
Task 3: ✅ 成功 (30分鐘)
Task 4: ❌ 失敗 (15分鐘)

Repair Run：
Task 1: 跳過（已成功）
Task 2: 跳過（已成功）
Task 3: 跳過（已成功）
Task 4: ▶️ 重新執行

時間比較：
├── 完整重跑 → 2小時+
└── Repair → 只需執行 Task 4
```

---

## ❌ 錯誤選項排除

### A. 刪除失敗 Run，啟動新 Run
**為什麼錯誤？**
- **會重跑所有任務，浪費時間**
- 已成功的任務會重複執行

### B. 保留失敗 Run，啟動新 Run
**為什麼錯誤？**
- **同樣會重跑所有任務**
- 不是最佳化的做法

### C. 重新執行所有任務
**為什麼錯誤？**
- **同樣浪費時間**
- 沒有利用 Repair 功能

**[返回題目](#question-044)**


你可以把 Repair run 想成：Databricks 的 Workflows/Jobs 其實是在跑一張「Task DAG（有依賴關係的任務圖）」，每個 task 都是一個可獨立重跑的 execution unit。Repair 的「原理」不是把整個 2 小時的流程「從失敗點接著往下跑（像程式斷點續跑）」；而是 在同一個 job run 的脈絡下，挑出需要重做的 task 子集合，重新排程執行，跳過已成功且不受影響的部分。  ￼

下面用更工程化的角度拆開：

1) Databricks 在 “Run” 裡到底記了什麼

一個 Job Run 會記錄（至少）：
	•	這次 run 的 task DAG、每個 task 的狀態（success/failed/skipped…）、開始/結束時間、輸出 log
	•	以及當下的 job/task 設定快照（例如 cluster spec、libraries、parameters…等）  ￼

所以你在 UI 看到的那張「這次 run 跑到哪、哪個 task 掛了」其實就是 orchestrator 的狀態機 + DAG 執行紀錄。

2) Repair run 的核心：只重跑「失敗 + 受影響」的 task

Repair run 的語意是：
	•	把指定的 task（通常是 failed 的那個）重新跑一次
	•	並且把它 downstream 依賴到的 task 一起重跑（因為上游輸出可能改變，downstream 的結果就不可信了）  ￼

官方 API 也直接講得很明白：repair 是 “Re-run one or more tasks”，而且 tasks 是「作為原本那個 job run 的一部分」被重跑，並且使用「目前（current）」的 job/task 設定。  ￼

這就是為什麼它能省時間：它不是重新排整張 DAG，而是排一個「必要的子圖」。

3) 它“不是”什麼：不是 notebook cell-level 的續跑

Repair 不會把 task 執行到一半的 process/memory 狀態留下來讓你接著跑。
	•	一個 task（例如 Notebook task、Python wheel task、SQL task）repair 時通常是 整個 task 從頭重新執行。
	•	能不能「看起來像接續」取決於你 task 的輸出是否已經落到外部可重用的持久層（例如 Delta 表、檔案、checkpoint）。這個“可接續”是 你的資料寫入/狀態設計提供的，不是 repair 魔法。  ￼

4) 為什麼要重跑 downstream：資料一致性與決定性

假設最後一個 task 失敗，但你修了它（例如修 bug、補權限、換參數），那它的輸出可能不同：
	•	downstream 如果不重跑，你會得到「上游已變、下游仍是舊版本」的混合結果。
	•	所以 repair 的預設策略通常是：重跑你選的點 + 其後所有依賴它的點，確保整體結果一致。  ￼

5) 真正的風險點（也是考點）：要靠“可重跑/冪等”來保證正確

Repair 能省時間，但不保證你“重跑就一定正確”，因為：
	•	如果你的 task 不是冪等（例如 append 重複寫、沒有用 transaction/merge、沒有 checkpoint），repair 可能造成重覆資料或髒寫。
	•	所以在多 task 長流程裡，常見最佳實務是讓各階段輸出落到 可追蹤、可覆寫、可 checkpoint 的儲存層（Delta 交易性、Structured Streaming checkpoint 等）。這樣 repair 才真的既快又穩。  ￼
