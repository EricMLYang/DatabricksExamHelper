## 📍 考點識別

**題目關鍵字：**
- **File Statistics**: 檔案統計資訊

- **nested fields**: 巢狀欄位

---

## ✅ 正解說明
### 為什麼 B 是錯誤的敘述（正確答案）？

**巢狀欄位確實會計入 32 欄位限制**：
- Nested fields（巢狀欄位）會被計算在內
- 例如：4 個 struct 欄位各有 8 個巢狀欄位 = 32 欄位
- 敘述說「不計入」是錯誤的

#### 32 欄位計算範例
```
Schema 範例：
├── id (INT)              → 1
├── name (STRING)         → 1
├── address (STRUCT)
│   ├── street (STRING)   → 1
│   ├── city (STRING)     → 1
│   ├── zip (STRING)      → 1
│   └── country (STRING)  → 1
├── contact (STRUCT)
│   ├── email (STRING)    → 1
│   └── phone (STRING)    → 1
└── ...

計算方式：所有欄位（包含巢狀）都計入
```

#### 官方說明
```
Delta Lake 統計資訊收集：
├── 預設收集前 32 欄位的統計資訊
├── 巢狀欄位會被計入 32 欄位限制
├── 超過 32 欄位的部分不會收集統計
└── 可以透過設定調整收集的欄位數
```

---

## ❌ 其他選項為何正確

### A. 高基數字串欄位的統計資訊通常沒有用
**這是正確的敘述**：
- 高基數（high cardinality）欄位的 min/max 統計意義不大
- 例如：UUID、email 欄位的 min/max 無法有效過濾
- Data skipping 在這類欄位上效果有限

```
統計資訊效用：
├── 低基數欄位（如日期）→ 統計有用 ✅
├── 數值欄位（如金額）→ 統計有用 ✅
└── 高基數字串（如 UUID）→ 統計無用 ❌
```

### C. Delta Lake 在 Transaction Log 中捕捉統計資訊
**這是正確的敘述**：
- 統計資訊存在 `_delta_log` 目錄
- 每個新增的資料檔案都有對應的統計
- 用於查詢優化的 data skipping

### D. 統計資訊用於 data skipping
**這是正確的敘述**：
- 選擇性查詢可以跳過不相關的檔案
- 利用 min/max 統計判斷檔案是否可能包含目標資料
- 顯著減少需要讀取的資料量

## 🧠 記憶法
### 口訣
**「巢狀欄位也計入，32 欄統計要小心」**

### File Statistics 重點整理
| 特性 | 說明 |
|------|------|
| 收集欄位數 | 預設前 32 欄位 |
| 巢狀欄位 | 計入 32 欄位限制 |
| 統計類型 | min, max, null count |
| 儲存位置 | Transaction Log |
| 用途 | Data Skipping |

### 調整統計欄位數
```sql
-- 調整收集統計的欄位數
ALTER TABLE my_table
SET TBLPROPERTIES (
    'delta.dataSkippingNumIndexedCols' = '50'
);

-- 或在建立表格時設定
CREATE TABLE my_table (...)
TBLPROPERTIES (
    'delta.dataSkippingNumIndexedCols' = '50'
);
```

### 統計資訊最佳化
```
如何優化統計資訊的效用？

1. 將常用過濾欄位放在前 32 欄
2. 避免在前 32 欄放高基數字串
3. 使用 ZORDER 在高選擇性欄位
4. 考慮調整 dataSkippingNumIndexedCols
```

### Data Skipping 原理
```
查詢：SELECT * FROM table WHERE date = '2024-01-15'

檔案統計：
├── file1: date_min='2024-01-01', date_max='2024-01-10' → 跳過
├── file2: date_min='2024-01-11', date_max='2024-01-20' → 讀取
└── file3: date_min='2024-01-21', date_max='2024-01-31' → 跳過

結果：只讀取 file2，大幅減少 I/O
```
