## 題目內容
### 題幹
<!-- ⚠️ 保持英文原文，不要翻譯 -->
The data engineering team noticed that a partitioned Delta Lake table is suffering greatly. They are experiencing slowdowns for most general queries on this table.

The team tried to run an OPTIMIZE command on the table, but this did not help to resolve the issue.

Which of the following likely explains the cause of these slowdowns?

### 選項
<!-- ⚠️ 保持英文原文，不要翻譯 -->
- **A.** They are applying the OPTIMIZE command on the whole table. It must be applied at each partition separately.
- **B.** They are applying the OPTIMIZE command without ZORDER. Z-ordering is needed on the partitioning columns.
- **C.** The table is over-partitioned or incorrectly partitioned. This requires a full rewrite of all data files to resolve the issue.
- **D.** The table has too many old data files that need to be purged. They need to run a VACUUM command instead.

# 題目解析

---

## 📍 考點識別
**核心技術:** Delta Lake 分區策略
**關鍵概念:** Over-partitioning、OPTIMIZE 限制
**題目關鍵字：**
- **partitioned Delta Lake table**: 已分區的表格
- **OPTIMIZE did not help**: OPTIMIZE 沒有幫助
- **slowdowns for most general queries**: 大部分查詢都變慢

---

## ✅ 正解說明
### 為什麼 C 是正確答案？

**Over-partitioning 會導致嚴重的效能問題**：
- OPTIMIZE 無法跨分區合併檔案
- 每個分區可能只有小檔案
- 需要完全重寫表格才能解決

#### Over-partitioning 問題
```
Over-partitioning 的影響：

分區過細的表格：
├── partition=2024-01-01-00/  (10 KB)
├── partition=2024-01-01-01/  (15 KB)
├── partition=2024-01-01-02/  (8 KB)
...
└── partition=2024-12-31-23/  (12 KB)

    ↓ 8760 個分區，每個只有小檔案

問題：
├── 大量小檔案 → 檔案列舉時間長
├── OPTIMIZE 無法合併 → 每個分區獨立處理
├── 元數據龐大 → Transaction Log 負擔
└── 查詢效能差 → 無法有效 data skipping
```

#### 為什麼 OPTIMIZE 無法解決？
```
OPTIMIZE 的限制：
├── 只能在分區內合併檔案
├── 無法跨分區合併
├── 如果每個分區都是小檔案
│   └── OPTIMIZE 後仍然是小檔案
└── 必須重新設計分區策略
```

#### 解決方案
```sql
-- 完全重寫表格（改變分區策略）

-- 方法 1: 建立新表格，減少分區粒度
CREATE TABLE new_table
PARTITIONED BY (date)  -- 改用 date 而非 hour
AS SELECT * FROM old_table;

-- 方法 2: 使用 Liquid Clustering 取代 Partition
CREATE TABLE new_table
CLUSTER BY (date, region)
AS SELECT * FROM old_table;

-- 方法 3: 如果不需要分區
CREATE TABLE new_table
AS SELECT * FROM old_table;
```

## ❌ 錯誤選項排除

### A. OPTIMIZE 必須對每個分區分別執行
**為什麼錯誤？**
- **OPTIMIZE 可以對整個表格執行**
- 它會自動處理所有分區
- 不需要手動對每個分區執行

```sql
-- 這是正確的（對整個表格）
OPTIMIZE my_table;

-- 這也是正確的（指定分區）
OPTIMIZE my_table WHERE date = '2024-01-01';

-- 但問題不在於執行方式，而是分區策略本身
```

### B. 需要 ZORDER 在分區欄位上
**為什麼錯誤？**
- **不應該對分區欄位使用 ZORDER**
- ZORDER 用於非分區欄位的資料佈局優化
- 分區欄位已經按照值分組，ZORDER 無意義

```
ZORDER 使用原則：
├── 分區欄位 → 不需要 ZORDER
├── 高基數篩選欄位 → 適合 ZORDER
└── 問題不在 ZORDER，而是 over-partitioning
```

### D. 需要 VACUUM 清理舊檔案
**為什麼錯誤？**
- **VACUUM 清理的是舊版本檔案，不是小檔案**
- VACUUM 不會改變檔案大小
- 問題是分區策略，不是舊檔案

```
VACUUM vs OPTIMIZE：
├── VACUUM → 清理 Time Travel 舊版本
├── OPTIMIZE → 合併小檔案
└── 但 over-partitioning 兩者都無法解決
```

## 🧠 記憶法

### 分區策略最佳實踐
| 建議 | 說明 |
|------|------|
| 每個分區至少 1 GB | 避免小檔案問題 |
| 分區數量 < 10,000 | 避免元數據膨脹 |
| 使用低基數欄位 | 如日期，而非時間戳 |
| 考慮 Liquid Clustering | 新專案建議使用 |

### Over-partitioning 徵兆
```
如何判斷 over-partitioning？
├── 大量分區目錄
├── 每個分區只有小檔案
├── 查詢全表非常慢
├── OPTIMIZE 效果不佳
└── DESCRIBE DETAIL 顯示大量檔案
```

### 分區策略選擇
```
分區策略決策：

資料量大（TB 級別）？
├── 是 → 考慮分區
│   └── 分區粒度選擇：
│       ├── date（日）→ 通常最佳
│       ├── month（月）→ 較大表格
│       └── 避免 hour/minute 級別
└── 否 → 不分區或用 Liquid Clustering
```
